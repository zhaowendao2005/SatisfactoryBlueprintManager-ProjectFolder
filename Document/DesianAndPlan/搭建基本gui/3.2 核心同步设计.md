# 蓝图管理器扩展 - 存档同步系统设计方案

## 📋 第一部分：设计概览

**【目标】**：实现蓝图库与游戏存档目录的双向同步机制，支持路径配置、差异检测、备份功能

**【范围】**：
- ✅ **在范围内**：
  - 存档目录选择与配置
  - 默认蓝图库/备份目录配置
  - 蓝图对象（.sbp + .sbpcfg）的双向同步
  - 路径索引构建与映射
  - 同步模式选择（全量/差异/最新/保存为新版本）
  - 文件占用检测与错误处理
  - UI 组件（TitleCard、SaveGameSelector、同步控制器）

- ❌ **不在范围内**：
  - 蓝图文件的解析与编辑
  - 游戏进程检测
  - 自动备份调度
  - 云同步功能

**【技术栈决策】**：
- **路径处理**：Node.js `path` 模块（统一使用正斜杠存储）
- **文件操作**：Node.js `fs.promises`（异步操作，支持大文件）
- **用户目录通配**：`electron.app.getPath('userData')` + `os.userInfo().username`
- **索引存储**：JSON 文件存储在 `{userData}/Data/blueprint-index.json`
- **文件占用检测**：`fs.open()` + `'r+'` 模式测试
- **差异检测**：基于文件修改时间（`mtime`）+ 文件大小

**【架构模式】**：
- **分层架构**：UI 层 → Store 层 → Datasource 层 → IPC 层 → Service 层
- **策略模式**：同步模式使用策略对象（SyncStrategy）
- **索引器模式**：蓝图路径映射使用索引器（BlueprintIndexer）

**【核心约束】**：
- 单次同步最大文件数：1000 个蓝图对象
- 单文件最大尺寸：100MB
- 文件占用检测超时：5s
- 路径长度限制：Windows 260 字符（需提示用户）
- 备份保留策略：限制总大小 1GB，超过则删除最旧的备份

// ==================== 类型定义 ====================

/**
 * 同步模式枚举
 */
type SyncMode = 'library-to-game' | 'game-to-library'

/**
 * 游戏→库同步策略
 */
type GameToLibraryMode = 'diff' | 'full' | 'latest' | 'new-version'

/**
 * 蓝图对象（.sbp + .sbpcfg 对）
 */
interface BlueprintPair {
  sbpPath: string          // .sbp 文件完整路径
  cfgPath: string | null   // .sbpcfg 文件完整路径（可能不存在）
  basename: string         // 文件基础名（不含后缀）
  lastModified: number     // 最后修改时间戳（取 sbp 的 mtime）
}

/**
 * 蓝图索引条目
 */
interface IndexEntry {
  fullPath: string         // 蓝图在源中的完整路径
  sourceName: string       // 所属源的名称
  relativePath: string     // 相对于源根目录的路径
  lastModified: number     // 索引时的修改时间
}

/**
 * 蓝图索引结构
 * @注意事项 basename 可能对应多个源路径（重名蓝图）
 */
interface BlueprintIndex {
  version: string                    // 索引版本
  createdAt: number                  // 创建时间
  entries: Map<string, IndexEntry[]> // key = basename（不含后缀），value = 可能的源路径列表
}

/**
 * 同步配置
 */
interface SyncConfig {
  saveGameBasePath: string           // 存档基础路径（默认：%LOCALAPPDATA%/FactoryGame/Saved/SaveGames/blueprints）
  selectedSaveGame: string | null    // 当前选中的存档名称
  libraryPath: string                // 默认蓝图库路径（默认：{userData}/Data/DefaultBlueprintRepository）
  backupPath: string                 // 备份目录路径（默认：{userData}/Data/BlueprintBackup）
  autoBackup: boolean                // 是否自动备份（默认 true）
}

/**
 * 库→游戏同步参数
 */
interface SyncLibraryToGameParams {
  targetPath: string                 // 游戏存档蓝图目录（完整路径）
  blueprints: ActiveBlueprintNode[]  // 激活的蓝图节点列表
  backupPath?: string                // 备份目录（如果提供，先备份）
  onProgress?: (progress: SyncProgress) => void  // 进度回调
}

/**
 * 游戏→库同步参数
 */
interface SyncGameToLibraryParams {
  sourcePath: string                 // 游戏存档蓝图目录
  mode: GameToLibraryMode            // 同步策略
  index: BlueprintIndex              // 蓝图索引
  fallbackPath: string               // 兜底目录（找不到映射时使用）
  onProgress?: (progress: SyncProgress) => void
}

/**
 * 同步进度
 */
interface SyncProgress {
  total: number                      // 总文件数
  completed: number                  // 已完成
  failed: number                     // 失败
  skipped: number                    // 跳过
  current: string                    // 当前处理的文件名
}

/**
 * 同步结果
 */
interface SyncResult {
  succeeded: BlueprintPair[]         // 成功同步的蓝图对
  failed: Array<{ pair: BlueprintPair, error: string }>  // 失败的蓝图对及错误信息
  skipped: Array<{ pair: BlueprintPair, reason: string }> // 跳过的蓝图对及原因
  backupPath?: string                // 备份路径（如果创建了备份）
  duration: number                   // 同步耗时（毫秒）
}

/**
 * 文件占用检测结果
 */
interface FileLockStatus {
  isLocked: boolean                  // 是否被占用
  lockedBy?: string                  // 占用进程（Windows 可通过 handle.exe 获取，简化版仅返回"游戏进程"）
}

## ⚠️ 第五部分：关键决策点与实施注意事项

### 决策点 1：如何处理重名蓝图的映射冲突？

**选择**：使用索引器记录所有可能的源路径，同步时如果发现多个匹配则跳过并警告

**理由**：
- 路径是唯一可靠的标识（basename 可能重复）
- 用户可能从不同源添加了同名蓝图
- 自动选择可能导致错误覆盖

**实施要点**：
- 索引结构使用 `Map<basename, IndexEntry[]>`，允许一对多
- `BlueprintIndexer.querySource()` 返回数组
- 同步时检查数组长度：
  - `length === 0` → 使用 fallbackPath
  - `length === 1` → 使用唯一匹配
  - `length > 1` → 弹出选择对话框，让用户逐个处理：
    * 显示蓝图名称和所有候选源路径
    * 用户可选择其中一个路径进行同步
    * 提供"跳过此蓝图"选项
    * 提供"全部使用兜底目录"快捷选项
- 对话框支持批量操作：记住用户选择，对后续重名蓝图应用相同策略

**反模式**：
- ❌ 不要自动选择第一个匹配（可能不是用户期望的）
- ❌ 不要在后台静默跳过（用户应明确知晓并决策）

---

### 决策点 2：文件占用检测的实现方式？

**选择**：使用 `fs.open()` 读写模式尝试打开，捕获 EBUSY/EPERM 错误

**理由**：
- 跨平台兼容（Windows/Linux 都支持）
- 无需额外依赖
- 占用时会抛出可预测的错误码

**实施要点**：
```typescript
async checkFileLock(filePath: string, timeout = 5000): Promise<FileLockStatus> {
  return new Promise((resolve) => {
    const timer = setTimeout(() => resolve({ isLocked: false }), timeout)
    
    fs.open(filePath, 'r+')
      .then(fd => {
        fs.close(fd)
        clearTimeout(timer)
        resolve({ isLocked: false })
      })
      .catch(error => {
        clearTimeout(timer)
        if (error.code === 'EBUSY' || error.code === 'EPERM') {
          resolve({ isLocked: true, lockedBy: '游戏进程' })
        } else {
          resolve({ isLocked: false })
        }
      })
  })
}
```

**错误处理**：
- 如果文件被占用 → 记录到 `SyncResult.failed`，error = "文件被游戏进程占用，请关闭游戏后重试"
- 超时视为未占用（避免卡死）

**反模式**：
- ❌ 不要使用 `lsof`/`handle.exe`（依赖外部工具）
- ❌ 不要无限等待（设置超时）

---

### 决策点 3：备份策略如何设计？

**选择**：时间戳目录 + 完整复制 + 总大小限制 1GB

**理由**：
- 时间戳目录便于识别备份时间
- 完整复制确保可恢复（不使用增量备份，避免复杂性）
- 限制总大小避免占用过多磁盘空间

**实施要点**：
- 备份目录命名：`backup-{YYYYMMDD-HHmmss}`（例如 `backup-20251105-143022`）
- 使用 `fs.cp(source, dest, { recursive: true })` 递归复制
- 清理逻辑：
  1. 读取 backupBaseDir 下所有以 `backup-` 开头的目录
  2. 计算所有备份的总大小
  3. 如果总大小超过 1GB：
     - 按目录名排序（字典序即时间序，最旧的在前）
     - 逐个删除最旧的备份，直到总大小 < 1GB
  4. 每次创建新备份后执行清理逻辑
- 仅在库→游戏同步时自动备份（游戏→库不备份，因为源已在蓝图库中）

**反模式**：
- ❌ 不要使用增量备份（复杂度高，恢复困难）
- ❌ 不要压缩备份（蓝图文件已较小，压缩收益低）
- ❌ 不要固定备份数量（可能导致空间浪费或不足）

---

### 决策点 4：差异检测如何实现？

**选择**：基于 `mtime`（修改时间）+ 文件大小

**理由**：
- `mtime` 是文件系统原生属性，读取快速
- 文件大小可快速排除明显不同的文件
- 蓝图文件不适合内容哈希（文件可能很大，100MB）

**实施要点**：
```typescript
// diff 模式：仅同步更新的文件
if (mode === 'diff') {
  const sourceStat = await fs.stat(sourcePath)
  const destStat = await fs.stat(destPath).catch(() => null)
  
  if (destStat) {
    const shouldUpdate = 
      sourceStat.mtimeMs > destStat.mtimeMs || 
      sourceStat.size !== destStat.size
    
    if (!shouldUpdate) {
      // 跳过，目标已是最新
      continue
    }
  }
}

// latest 模式：保留最新的
if (mode === 'latest') {
  const sourceStat = await fs.stat(sourcePath)
  const destStat = await fs.stat(destPath).catch(() => null)
  
  if (destStat && destStat.mtimeMs > sourceStat.mtimeMs) {
    // 目标更新，跳过
    continue
  }
}
```

**反模式**：
- ❌ 不要使用文件哈希（性能差）
- ❌ 不要仅比较文件名（不可靠）

---

### 决策点 5：新版本模式的文件名如何生成？

**选择**：`{basename}.{timestamp}.sbp` 格式

**理由**：
- 时间戳确保唯一性
- 保留原始名称便于识别
- 符合用户提出的格式要求

**实施要点**：
```typescript
// new-version 模式
if (mode === 'new-version') {
  const timestamp = Date.now()
  const ext = path.extname(sourcePath)        // .sbp 或 .sbpcfg
  const basename = path.basename(sourcePath, ext)
  const newName = `${basename}.${timestamp}${ext}`
  
  await FileOperationService.copyBlueprintPair(sourcePath, destDir, {
    newName: newName.replace(ext, '')  // 不含后缀的新名称
  })
}
```

- 同时处理 .sbp 和 .sbpcfg，确保时间戳一致
- 如果目标已存在同名文件（极低概率），追加 `-1`、`-2` 后缀

**反模式**：
- ❌ 不要使用 UUID（不便于识别）
- ❌ 不要使用递增序号（需维护状态）

---

### 决策点 6：兜底目录的文件名冲突如何处理？

**选择**：文件名前加 4 位哈希前缀：`{hash4}-{basename}.sbp`

**理由**：
- 避免与现有文件冲突
- 保留原始名称便于识别
- 哈希基于路径，同一文件多次同步生成相同前缀

**实施要点**：
```typescript
const generateHash4 = (str: string): string => {
  let hash = 0
  for (let i = 0; i < str.length; i++) {
    const char = str.charCodeAt(i)
    hash = ((hash << 5) - hash) + char
    hash = hash & hash
  }
  return Math.abs(hash % 10000).toString().padStart(4, '0')
}

// 使用原始完整路径计算哈希（确保唯一性）
const hash = generateHash4(originalFullPath)
const newName = `${hash}-${basename}`
```

**反模式**：
- ❌ 不要使用随机哈希（每次同步生成不同名称）
- ❌ 不要仅检查冲突后追加序号（不可预测）

## 🔒 安全隐患与风险点

### 风险点 1：覆盖操作不可逆

**隐患**：库→游戏同步会直接覆盖游戏目录，用户可能丢失在游戏中修改的蓝图

**缓解措施**：
- 强制警告对话框 + "我已知晓风险"复选框
- 默认启用自动备份
- 备份路径明确显示在结果对话框中

---

### 风险点 2：重名蓝图的误操作

**隐患**：用户可能无意中从不同源添加了同名蓝图，游戏→库同步时可能覆盖错误的源

**缓解措施**：
- 索引构建时检测重名，记录警告日志
- 同步时弹出选择对话框，显示所有候选源路径
- 用户可逐个选择正确的目标路径，或选择跳过/使用兜底目录
- 对话框支持批量策略，避免重复选择

---

### 风险点 3：文件占用检测的误报/漏报

**隐患**：
- 误报：文件未被占用但检测为占用 → 用户无法同步
- 漏报：文件被占用但检测为未占用 → 复制失败

**缓解措施**：
- 设置 5s 超时，避免误报导致卡死
- 复制失败时捕获异常，显示具体错误信息
- 提示用户"如果确认游戏已关闭，请重试"

---

### 风险点 4：路径长度超限（Windows）

**隐患**：Windows 路径限制 260 字符，嵌套深的蓝图可能无法复制

**缓解措施**：
- 复制前检查路径长度
- 超限时跳过并记录 error = "路径过长（>260 字符），请缩短目录层级"
- 文档中提示用户将蓝图源放在浅层目录

---

### 风险点 5：并发同步冲突

**隐患**：用户同时触发两次同步，可能导致文件损坏

**缓解措施**：
- `SyncOperationStore` 维护 `isSyncing` 状态
- 同步中时，禁用同步按钮
- 尝试并发同步时，弹出提示"已有同步任务进行中"
