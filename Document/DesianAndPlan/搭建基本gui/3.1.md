# 配置管理与蓝图激活系统 - 完整设计方案（修订版）

## 📋 第一部分：设计概览

**【目标】**：实现配置管理系统，支持配置的创建、切换、重命名、删除，以及单个/批量蓝图激活，并将配置数据持久化到本地文件系统

**【范围】**：
- **在范围内**：
  - 配置文件的 CRUD 操作（无默认配置）
  - 配置选择器 UI（必须选择配置才能激活蓝图）
  - 单个蓝图激活（添加到"未分组"）
  - 批量蓝图激活（通过复选框 + 上下文菜单）
  - 智能分组规则（选中蓝图的直接父目录作为分组）
  - 配置切换时的数据同步
- **不在范围内**：
  - 默认配置的自动创建
  - 树节点的拖拽排序（后续实现）
  - 蓝图文件内容的解析

**【技术栈决策】**：
- 持久化层：Electron 主进程 fs.promises
- IPC 通信：contextBridge + ipcMain/ipcRenderer
- 状态管理：Pinia Store（BlueprintSource + ActiveBlueprint）
- UI 组件：Element Plus（表单、下拉选择器、上下文菜单、复选框）
- 数据格式：JSON

**【架构模式】**：分层架构（Presentation → Store → Datasource → IPC → FileSystem）

**【核心约束】**：
- 配置文件大小：单文件 < 10MB
- 配置加载时间：< 500ms
- 配置切换时间：< 200ms
- 配置名称长度：1-50 字符
- **强制规则**：激活蓝图前必须选择配置，否则弹出错误提示

## 🏗️ 第二部分：模块划分与职责

```
配置管理与激活系统
├─ ConfigManager 组件（职责：配置选择、创建、重命名、删除的 UI）
│   ├─ 输入：无（从 Store 读取配置列表）
│   ├─ 输出：用户操作事件（select/create/rename/delete）
│   └─ 关键逻辑：
│       1. 下拉选择器显示配置列表，空状态提示"请先创建配置"
│       2. "新建配置"按钮 → 弹出输入框 → Store.createConfig(name)
│          - 创建成功后自动切换到新配置
│          - 新配置包含一个"未分组"节点（id: "ungrouped", type: "group"）
│       3. "重命名"按钮 → 仅当有选中配置时可用 → Store.renameConfig(id, newName)
│       4. "删除"按钮 → 仅当有选中配置时可用 → 确认对话框 → Store.deleteConfig(id)
│       5. 配置切换时 → Store.switchConfig(id) → 更新蓝图源和已激活蓝图
│
├─ BlueprintSource 激活逻辑扩展（职责：单个/批量激活蓝图）
│   ├─ TreeNode 工具箱扩展
│   │   └─ 关键逻辑：
│   │       1. 蓝图节点的"激活"按钮点击时：
│   │          - 检查是否有选中配置 → 无则弹出错误："请先创建或选择一个配置"
│   │          - 有配置 → Store.activateBlueprint(blueprintNode)
│   │          - 添加到当前配置的"未分组"节点下
│   │
│   ├─ TreeView 复选框与上下文菜单
│   │   ├─ 输入：用户选中的节点 keys（el-tree 的 checked-keys）
│   │   ├─ 输出：批量激活事件
│   │   └─ 关键逻辑：
│   │       1. el-tree 开启 show-checkbox
│   │       2. 右键菜单（ContextMenu）显示"激活选中项"选项
│   │       3. 点击"激活选中项"时：
│   │          - 检查是否有选中配置 → 无则弹出错误
│   │          - 获取 checked-keys（选中的节点 id 列表）
│   │          - 调用 Store.batchActivateBlueprints(checkedKeys)
│   │
│   └─ 批量激活智能分组算法（职责：根据选中节点构建分组结构）
│       ├─ 输入：checkedKeys: string[]（选中的节点 id 列表）
│       ├─ 输出：ActiveBlueprintNode[]（带分组的树结构）
│       └─ 关键逻辑：
│           1. 遍历 checkedKeys，区分目录节点和蓝图节点
│           2. 对于每个选中的蓝图节点：
│              a. 找到其直接父目录节点（parentNode）
│              b. 检查 parentNode 是否已在结果中：
│                 - 不存在 → 创建父目录分组节点
│                 - 存在 → 复用
│              c. 将蓝图节点添加到父目录分组的 children 中
│           3. 对于选中的目录节点：
│              a. 如果目录本身被选中，递归获取其所有蓝图子节点
│              b. 将目录作为分组节点，包含所有蓝图子节点
│           4. 未匹配到任何父目录的蓝图 → 添加到"未分组"
│           5. 示例：
│              选中：/source1/dir1/bp1.sbp, /source1/dir1/bp2.sbp, /source1/dir2/bp3.sbp
│              结果：
│              - 分组：dir1（来自 /source1/dir1）
│                - bp1
│                - bp2
│              - 分组：dir2（来自 /source1/dir2）
│                - bp3
│
├─ ConfigDatasource（职责：配置数据的持久化）
│   ├─ 输入：ConfigFileData
│   ├─ 输出：Promise<ConfigFileData>
│   ├─ 依赖：window.configAPI
│   └─ 关键逻辑：
│       1. listConfigs() → IPC 列出所有配置文件
│       2. loadConfig(id) → 读取配置文件，解析为 ConfigFileData
│       3. saveConfig(data) → 序列化后写入 {userData}/Data/{id}.json
│       4. deleteConfig(id) → 删除文件
│       5. renameConfig(id, name) → 读取 → 修改 name 字段 → 写入
│
├─ ConfigFileService（Electron 主进程，职责：文件系统操作）
│   ├─ 输入：IPC 请求（configId, configData）
│   ├─ 输出：IPC 响应
│   ├─ 依赖：fs.promises, path, electron.app.getPath('userData')
│   └─ 关键逻辑：
│       1. 初始化：检查 userData/Data 目录，不存在则创建
│       2. ⚠️ 不创建默认配置，首次启动时 listConfigs 返回空数组
│       3. listConfigs：fs.readdir 过滤 *.json，提取 id 和 name
│       4. loadConfig：fs.readFile → JSON.parse，捕获解析错误
│       5. saveConfig：JSON.stringify(data, null, 2) → fs.writeFile
│       6. deleteConfig：fs.unlink
│   └─ 错误处理：
│       - 文件不存在：返回 null
│       - 解析错误：记录日志，返回 null
│       - 写入失败：抛出错误
│
└─ ActiveBlueprint Store 扩展（职责：配置状态与激活蓝图的同步）
    ├─ 新增状态：
    │   - currentConfigId: string | null（当前选中的配置 id）
    │   - configList: ConfigMeta[]（配置列表）
    │   - treeData: ActiveBlueprintNode[]（当前配置的树数据）
    │
    ├─ 新增 actions：
    │   - loadConfigList() → 加载所有配置的元信息
    │   - createConfig(name) → 生成 id → 创建包含"未分组"的初始配置 → 切换
    │   - switchConfig(id) → 保存当前配置 → 加载新配置 → 更新 treeData
    │   - renameConfig(id, name) → 更新文件 name 字段 → 刷新列表
    │   - deleteConfig(id) → 删除文件 → 清空 currentConfigId → 清空 treeData
    │   - activateBlueprint(node) → 检查配置 → 添加到"未分组"
    │   - batchActivateBlueprints(checkedKeys) → 检查配置 → 智能分组 → 合并到 treeData
    │
    └─ 关键逻辑：
        1. 初始化时加载配置列表，读取 localStorage.lastConfigId
        2. 如果 lastConfigId 存在且有效，自动加载该配置
        3. 否则 currentConfigId = null，treeData = []
        4. 创建配置时，初始 tree 包含一个"未分组"节点：
           {
             id: "ungrouped",
             type: "group",
             name: "未分组",
             children: []
           }
        5. 激活单个蓝图：找到"未分组"节点 → 添加到其 children
        6. 批量激活：调用智能分组算法 → 合并到 treeData（避免重复）
        7. 配置切换时：保存当前 treeData → 加载新配置的 tree → 更新 treeData
```

## 🔌 第三部分：关键接口定义

```typescript
/**
 * 配置文件元信息
 */
interface ConfigMeta {
  id: string          // 配置 id（文件名，不含 .json）
  name: string        // 配置显示名称
  createdAt: number   // 创建时间戳
  updatedAt: number   // 更新时间戳
}

/**
 * 配置文件完整数据
 * @注意事项 存储在 {userData}/Data/{id}.json
 */
interface ConfigFileData {
  id: string                    // 配置 id
  name: string                  // 配置名称
  version: string               // 配置文件版本，初始 "1.0.0"
  createdAt: number             // 创建时间戳
  updatedAt: number             // 更新时间戳
  tree: ActiveBlueprintNode[]   // 激活的蓝图树（包含"未分组"）
}

/**
 * 激活蓝图树节点
 */
interface ActiveBlueprintNode {
  id: string                      // 节点 id
  type: 'group' | 'blueprint'     // 节点类型
  name: string                    // 显示名称
  children?: ActiveBlueprintNode[] // 子节点（仅 group 有）
  // 蓝图节点专有字段
  path?: string                   // 蓝图文件路径（type=blueprint 时必需）
  sourcePath?: string             // 来源路径（用于去重）
  metadata?: Record<string, unknown>
}

/**
 * 批量激活参数
 */
interface BatchActivateParams {
  checkedKeys: string[]           // 选中的节点 id 列表
  treeData: BlueprintNode[]       // 蓝图源的完整树数据（用于查找父节点）
}

/**
 * 批量激活结果
 */
interface BatchActivateResult {
  groups: ActiveBlueprintNode[]   // 新增的分组节点（带子蓝图）
  ungrouped: ActiveBlueprintNode[] // 添加到"未分组"的蓝图
}

/**
 * 配置管理数据源接口
 */
interface IConfigDatasource {
  listConfigs(): Promise<ConfigMeta[]>
  loadConfig(id: string): Promise<ConfigFileData | null>
  saveConfig(data: ConfigFileData): Promise<void>
  deleteConfig(id: string): Promise<void>
  renameConfig(id: string, newName: string): Promise<void>
}

/**
 * Electron IPC 配置 API
 */
interface ElectronConfigAPI {
  listConfigs(): Promise<ConfigMeta[]>
  loadConfig(id: string): Promise<ConfigFileData | null>
  saveConfig(data: ConfigFileData): Promise<void>
  deleteConfig(id: string): Promise<void>
  renameConfig(id: string, newName: string): Promise<void>
}

/**
 * ActiveBlueprint Store 扩展接口
 */
interface IActiveBlueprintStore {
  // 状态
  currentConfigId: string | null
  configList: ConfigMeta[]
  treeData: ActiveBlueprintNode[]
  
  // Actions
  loadConfigList(): Promise<void>
  createConfig(name: string): Promise<void>
  switchConfig(id: string): Promise<void>
  renameConfig(id: string, newName: string): Promise<void>
  deleteConfig(id: string): Promise<void>
  
  // 激活相关
  activateBlueprint(node: BlueprintNode): Promise<void>
  batchActivateBlueprints(params: BatchActivateParams): Promise<void>
  deactivateBlueprint(nodeId: string): Promise<void>
  
  // 辅助方法
  hasActiveConfig(): boolean  // 检查是否有选中配置
  getUngroupedNode(): ActiveBlueprintNode | undefined  // 获取"未分组"节点
}
```

## 📊 第四部分：数据流与状态机

### 数据流 1：配置创建与切换

```
用户点击"新建配置"
  --(输入配置名称)-->
ConfigManager 组件
  --(dispatch)-->
ActiveBlueprint Store.createConfig(name)
  --(生成 id = "config-" + Date.now())-->
  --(构建初始数据：tree = [未分组节点])-->
ConfigDatasource.saveConfig(initialData)
  --(IPC 请求)-->
Electron ConfigFileService.saveConfig()
  --(写入)-->
{userData}/Data/{id}.json
  --(保存成功)-->
Store.switchConfig(newId)
  --(更新状态：currentConfigId, treeData)-->
  --(localStorage.lastConfigId = newId)-->
UI 更新（配置选择器显示新配置，树视图显示"未分组"）
```

### 数据流 2：单个蓝图激活

```
用户点击蓝图节点的"激活"按钮
  --(blueprintNode)-->
TreeNode 组件.handleToggleActivate()
  --(检查 store.hasActiveConfig())-->
  
【情况 A：无配置】
  --> ElMessage.error("请先创建或选择一个配置")
  
【情况 B：有配置】
  --(dispatch)-->
ActiveBlueprint Store.activateBlueprint(blueprintNode)
  --(查找"未分组"节点)-->
  --(检查是否已激活：通过 sourcePath 去重)-->
  --(未激活 → 添加到 ungrouped.children)-->
  --(自动保存当前配置到文件)-->
TreeView 组件更新（"未分组"下显示新蓝图）
```

### 数据流 3：批量激活蓝图

```
用户勾选复选框（多个节点）
  --(el-tree checked-keys)-->
用户右键打开上下文菜单
  --(点击"激活选中项")-->
TreeView 组件.handleBatchActivate()
  --(检查 store.hasActiveConfig())-->
  
【情况 A：无配置】
  --> ElMessage.error("请先创建或选择一个配置")
  
【情况 B：有配置】
  --(获取 checkedKeys)-->
  --(dispatch)-->
ActiveBlueprint Store.batchActivateBlueprints({ checkedKeys, treeData })
  --(调用智能分组算法)-->
  
【智能分组算法】：
  1. 遍历 checkedKeys，区分目录和蓝图
  2. 对于蓝图节点：
     - 找到直接父目录（通过 path 解析）
     - 创建/复用父目录分组节点
     - 添加蓝图到分组的 children
  3. 对于目录节点：
     - 递归获取目录下所有蓝图
     - 将目录作为分组节点
  4. 返回：{ groups: [...], ungrouped: [...] }
  
  --(合并到 store.treeData)-->
  --(去重：检查 sourcePath)-->
  --(自动保存当前配置到文件)-->
TreeView 组件更新（显示新增的分组和蓝图）
```

### 配置状态机

```
应用启动
  -> [加载配置列表] -> IDLE
  -> [读取 localStorage.lastConfigId] ->
     -> [存在且有效] -> LOADING_CONFIG
     -> [不存在/无效] -> NO_CONFIG

NO_CONFIG（无配置状态）
  - currentConfigId = null
  - treeData = []
  - UI 显示："请先创建配置"
  -> [用户创建配置] -> CREATING

CREATING（创建配置中）
  -> [成功] -> SWITCHING（自动切换到新配置）
  -> [失败] -> ERROR -> NO_CONFIG

LOADING_CONFIG（加载配置中）
  -> [成功] -> ACTIVE
  -> [失败（文件损坏）] -> ERROR -> NO_CONFIG

ACTIVE（配置已加载）
  - currentConfigId != null
  - treeData 包含激活的蓝图树
  - 用户可以激活/取消激活蓝图
  -> [切换配置] -> SWITCHING
  -> [重命名] -> RENAMING
  -> [删除] -> DELETING
  -> [激活蓝图（无配置）] -> ERROR（不应发生，防御性检查）

SWITCHING（切换配置中）
  1. 保存当前配置到文件
  2. 加载新配置
  3. 更新 treeData
  -> [成功] -> ACTIVE
  -> [失败] -> ERROR -> ACTIVE（保持当前配置）

RENAMING（重命名中）
  -> [成功] -> ACTIVE（刷新配置列表）
  -> [失败] -> ERROR -> ACTIVE

DELETING（删除中）
  -> [成功] -> NO_CONFIG（currentConfigId = null）
  -> [失败] -> ERROR -> ACTIVE
```

## ⚠️ 第五部分：关键决策点与实施注意事项

### 决策点 1：不提供默认配置
- **选择**：首次启动时不创建任何配置，用户必须手动创建
- **理由**：
  - 用户明确要求
  - 避免用户不知道默认配置的存在
  - 强制用户理解配置的概念
- **实施要点**：
  - 应用启动时 `listConfigs()` 可能返回空数组
  - UI 显示空状态："暂无配置，请创建一个配置开始使用"
  - 激活蓝图前检查 `store.hasActiveConfig()`，无配置时弹出错误
  - localStorage.lastConfigId 可能为 null
- **反模式**：
  - ❌ 不要在后台偷偷创建默认配置
  - ❌ 不要在无配置时允许激活蓝图

### 决策点 2：配置初始结构包含"未分组"
- **选择**：创建配置时，初始 tree 包含一个固定的"未分组"节点
- **理由**：
  - 单个激活的蓝图需要一个默认位置
  - 避免空树状态
  - 用户体验更友好
- **实施要点**：
  - "未分组"节点固定 id: "ungrouped"
  - 单个激活时查找 `tree.find(n => n.id === 'ungrouped')`
  - "未分组"节点不可删除、不可重命名
  - 创建配置时的初始数据：
    ```json
    {
      "tree": [{
        "id": "ungrouped",
        "type": "group",
        "name": "未分组",
        "children": []
      }]
    }
    ```
- **反模式**：
  - ❌ 不要让用户手动创建"未分组"
  - ❌ 不要允许删除"未分组"节点

### 决策点 3：批量激活的智能分组规则
- **选择**：选中蓝图的**直接父目录**作为分组，不递归上级
- **理由**：
  - 符合用户直觉（蓝图在哪个文件夹，就归到哪个组）
  - 避免层级过深
  - 性能更好
- **实施要点**：
  - 算法伪代码：
    ```typescript
    function buildGroupsFromSelection(checkedKeys, sourceTree) {
      const blueprintMap = new Map() // key: parentPath, value: BlueprintNode[]
      
      for (const key of checkedKeys) {
        const node = findNodeById(sourceTree, key)
        
        if (node.type === 'blueprint') {
          // 提取父目录路径（去掉文件名）
          const parentPath = getParentPath(node.path)
          const parentNode = findNodeByPath(sourceTree, parentPath)
          
          if (!blueprintMap.has(parentPath)) {
            blueprintMap.set(parentPath, {
              group: createGroupFromDirectory(parentNode),
              blueprints: []
            })
          }
          
          blueprintMap.get(parentPath).blueprints.push(node)
        }
        
        if (node.type === 'directory') {
          // 递归获取目录下所有蓝图
          const blueprints = getAllBlueprintsInDirectory(node)
          blueprintMap.set(node.path, {
            group: createGroupFromDirectory(node),
            blueprints
          })
        }
      }
      
      // 转换为 ActiveBlueprintNode[]
      return Array.from(blueprintMap.values()).map(item => ({
        ...item.group,
        children: item.blueprints.map(bp => convertToActiveBlueprintNode(bp))
      }))
    }
    ```
  - 示例场景：
    ```
    源结构：
    /source1/
      dir1/
        bp1.sbp ✓ 选中
        bp2.sbp ✓ 选中
        subdir/
          bp3.sbp （未选中）
      dir2/
        bp4.sbp ✓ 选中
    
    结果：
    - 分组 "dir1"（来自 /source1/dir1）
      - bp1
      - bp2
    - 分组 "dir2"（来自 /source1/dir2）
      - bp4
    
    注意：bp3 未被包含，因为其父目录 subdir 未被选中
    ```
- **反模式**：
  - ❌ 不要递归添加所有上级目录（如 /source1 → dir1 → bp1）
  - ❌ 不要包含未选中蓝图所在的子目录

### 决策点 4：复选框与上下文菜单的集成
- **选择**：el-tree 开启 show-checkbox，右键菜单提供"激活选中项"
- **理由**：
  - 复选框是标准的多选交互
  - 右键菜单符合桌面应用习惯
  - 与单个激活（工具箱按钮）形成互补
- **实施要点**：
  - el-tree 配置：
    ```vue
    <el-tree
      show-checkbox
      :check-strictly="true"
      @check="handleCheck"
      @node-contextmenu="handleContextMenu"
    />
    ```
  - 右键菜单只在有勾选项时显示"激活选中项"
  - 激活后自动取消所有勾选（清空 checked-keys）
  - 上下文菜单组件位置：`BlueprintSource/ContextMenu.vue`
- **反模式**：
  - ❌ 不要使用 Ctrl+点击多选（不直观）
  - ❌ 不要在工具箱中添加批量激活按钮（占空间）

### 决策点 5：配置切换时的数据同步
- **选择**：切换前自动保存当前配置，切换后清空并加载新配置
- **理由**：
  - 防止数据丢失
  - 配置之间完全隔离
  - 用户体验流畅
- **实施要点**：
  - 切换流程：
    ```typescript
    async switchConfig(newId: string) {
      // 1. 保存当前配置
      if (this.currentConfigId && this.treeData.length > 0) {
        await this.saveCurrentConfig()
      }
      
      // 2. 加载新配置
      const configData = await configDatasource.loadConfig(newId)
      if (!configData) {
        throw new Error('配置加载失败')
      }
      
      // 3. 更新状态
      this.currentConfigId = newId
      this.treeData = configData.tree
      
      // 4. 持久化选择
      localStorage.setItem('lastConfigId', newId)
      
      // 5. 通知蓝图源刷新（如果需要）
      // blueprintSourceStore.refresh()
    }
    ```
  - 保存失败时询问用户是否继续
  - 加载失败时回退到之前的配置
- **反模式**：
  - ❌ 不要异步保存（可能来不及）
  - ❌ 不要合并配置数据（应该完全替换）

### 决策点 6：去重逻辑
- **选择**：通过 `sourcePath` 字段去重，避免重复激活同一蓝图
- **理由**：
  - 蓝图可能在不同分组中重复
  - 用户可能多次激活同一蓝图
- **实施要点**：
  - ActiveBlueprintNode 添加 `sourcePath` 字段（存储原始路径）
  - 激活前检查：
    ```typescript
    function isAlreadyActivated(sourcePath: string, tree: ActiveBlueprintNode[]): boolean {
      function traverse(nodes: ActiveBlueprintNode[]): boolean {
        for (const node of nodes) {
          if (node.type === 'blueprint' && node.sourcePath === sourcePath) {
            return true
          }
          if (node.children && traverse(node.children)) {
            return true
          }
        }
        return false
      }
      return traverse(tree)
    }
    ```
  - 重复激活时提示："该蓝图已激活"
- **反模式**：
  - ❌ 不要用 id 去重（分组的 id 可能与蓝图冲突）
  - ❌ 不要允许重复激活

### 智能分组算法伪代码

```typescript
// stores/BlueprintSource/index.ts
function buildGroupsFromSelection(
  checkedKeys: string[],
  sourceTree: BlueprintNode[]
): BatchActivateResult {
  const groupMap = new Map<string, {
    group: ActiveBlueprintNode,
    blueprints: BlueprintNode[]
  }>()
  
  const ungrouped: BlueprintNode[] = []
  
  for (const key of checkedKeys) {
    const node = findNodeById(sourceTree, key)
    
    if (!node) continue
    
    if (node.type === 'blueprint') {
      // 提取父目录路径
      const parentPath = extractParentPath(node.path)
      const parentNode = findNodeByPath(sourceTree, parentPath)
      
      if (parentNode && parentNode.type === 'directory') {
        // 添加到父目录分组
        if (!groupMap.has(parentPath)) {
          groupMap.set(parentPath, {
            group: createGroupFromDirectory(parentNode),
            blueprints: []
          })
        }
        groupMap.get(parentPath)!.blueprints.push(node)
      } else {
        // 无法确定父目录，添加到未分组
        ungrouped.push(node)
      }
    }
    
    if (node.type === 'directory') {
      // 递归获取目录下所有蓝图
      const blueprints = getAllBlueprintsInDirectory(node)
      groupMap.set(node.path, {
        group: createGroupFromDirectory(node),
        blueprints
      })
    }
  }
  
  // 转换为 ActiveBlueprintNode[]
  const groups = Array.from(groupMap.values()).map(item => ({
    ...item.group,
    children: item.blueprints.map(bp => convertToActiveBlueprintNode(bp))
  }))
  
  return {
    groups,
    ungrouped: ungrouped.map(bp => convertToActiveBlueprintNode(bp))
  }
}
```
