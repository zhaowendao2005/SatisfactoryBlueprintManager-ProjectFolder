# MainWindow 主窗口架构实施设计方案

## 📋 第一部分：设计概览

**【目标】**：构建 Electron 应用的主窗口架构，包含自定义标题栏、侧边导航栏和主内容区，替换原有 Home 页面结构

**【范围】**：
- **在范围内**：
  - 通用标题栏组件（General.Titlebar）实现窗口控制（最小化/最大化/关闭）
  - MainWindow 布局架构（标题栏+左导航+内容区）
  - 导航栏组件（Welcome/Blueprint 两个选项）
  - Element Plus 集成
  - 类型系统按架构规范组织
- **不在范围内**：
  - Welcome/Blueprint 页面的具体内容实现
  - 窗口拖拽、双击最大化等高级交互（后续迭代）
  - 导航栏的展开/收起动画（后续迭代）

**【技术栈决策】**：
- UI 组件库：Element Plus v2.x（原因：Electron 应用需要桌面级 UI 体验，Element Plus 与 Electron 集成良好）
- 窗口控制：Electron IPC 通信（原因：需要主进程控制窗口行为）
- 布局方案：Flexbox + CSS Grid（原因：简单高效，无需引入额外布局库）
- 状态管理：Pinia store（原因：导航状态需跨组件共享）
- 类型系统：TypeScript 严格模式（原因：符合项目 ESLint 规范）

**【架构模式】**：容器-展示组件模式（Container-Presentational Pattern）
- 容器组件：`MainWindow/layout.vue`（负责布局和数据编排）
- 展示组件：`General.Titlebar`、`MainWindow.Navbar`、`MainWindow.TitleBar`（负责 UI 渲染）

**【核心约束】**：
- 标题栏高度：固定 32px（Windows 标准）
- 左导航栏宽度：固定 60px（仅图标模式）
- 导航组占比：上组 5/6，下组 1/6（使用 flex-grow）
- TypeScript 严格模式：启用 `@typescript-eslint/consistent-type-imports`
- Electron IPC 安全：仅通过 preload 脚本暴露白名单 API

## 🏗️ 第二部分：模块划分与职责

**【状态管理说明】**：
- Vue 组件通过 `use[StoreName]` 组合式函数调用 Store 状态
- Store 中的响应式状态会自动内联到 Vue 组件的响应式系统中
- 组件只负责展示和交互，业务逻辑和状态由 Store 管理

## 🔌 第三部分：关键接口定义

**【类型组织原则】**：
- **前后端协同类型**：涉及 Electron 主进程与渲染进程通信的类型，必须放在 `public/types/{业务}/` 目录下
  - 示例：`public/types/window/` 存放窗口控制相关的跨进程类型（ElectronWindowAPI、WindowControlAction）
  - 示例：`public/types/app/` 存放应用配置相关的跨进程类型
- **前端专用类型**：仅在渲染进程使用的类型，放在对应的业务模块目录下
  - 示例：`GUI/pages/MainWindow/Shell/types.ts` 存放 MainWindow 导航栏相关的类型（NavItem、NavGroup）
- **组件内部类型**：仅在单个组件/模块内使用的类型，放在对应模块的 `types.ts` 文件中

## 📊 第四部分：数据流与状态机

### 数据流向

```
用户交互流：
  [用户点击窗口控制按钮]
    --(WindowControlAction)-->
  [General.Titlebar 组件]
    --(IPC 消息)-->
  [Electron Preload API]
    --(IPC 消息)-->
  [Electron 主进程]
    --(BrowserWindow API)-->
  [窗口状态变化]
    --(IPC 回调)-->
  [General.Titlebar 组件内状态更新]
    --(响应式更新)-->
  [UI 图标状态更新]

导航流：
  [用户点击导航项]
    --(NavItem)-->
  [MainWindow.Navbar 组件]
    --(router.push())-->
  [Vue Router]
    --(路由变化)-->
  [MainWindowNavbarStore.activeRoute 更新]
    --(响应式更新)-->
  [导航项激活状态更新]
```

### 窗口状态机

```
窗口状态：
  NORMAL（正常）
    -> [点击最大化按钮] -> MAXIMIZED（最大化）
    -> [点击最小化按钮] -> MINIMIZED（最小化）
    -> [点击关闭按钮] -> CLOSED（关闭，终态）
  
  MAXIMIZED（最大化）
    -> [点击还原按钮] -> NORMAL（正常）
    -> [点击关闭按钮] -> CLOSED（关闭，终态）
  
  MINIMIZED（最小化）
    -> [点击任务栏图标] -> NORMAL（正常）
    -> [点击关闭按钮] -> CLOSED（关闭，终态）
```

### 导航状态机

```
导航状态：
  NO_SELECTION（无选中）
    -> [应用启动] -> WELCOME_ACTIVE（Welcome 激活，默认）
  
  WELCOME_ACTIVE（Welcome 激活）
    -> [点击 Blueprint] -> BLUEPRINT_ACTIVE（Blueprint 激活）
  
  BLUEPRINT_ACTIVE（Blueprint 激活）
    -> [点击 Welcome] -> WELCOME_ACTIVE（Welcome 激活）
```

### 决策点 1：如何组织目录结构以符合架构规范？

**选择**：严格按照业务域划分，禁止在 `components/`、`types/`、`stores/`、`service/` 下直接放置文件

**理由**：保持架构清晰，避免文件散乱，符合项目架构规范要求

**实施要点**：

  - `types.ts`：内部类型（TitlebarProps 等）

  - `Shell/MainWindow.Navbar/index.vue`：主窗口导航栏
  - `Shell/MainWindow.Navbar/NavItem.vue`：导航项子组件
  - `Shell/types.ts`：Shell 层内部类型
- `GUI/stores/MainWindow.Navbar/`：MainWindow 导航栏状态管理
  - `index.ts`：MainWindowNavbarStore 实现
  - `types.ts`：Store 专用类型
- `GUI/types/window/`：窗口相关外部类型
  - `index.ts`：导出 ElectronWindowAPI、WindowControlAction
- `GUI/pages/MainWindow/Shell/types.ts`：MainWindow Shell 层类型（包含 NavItem、NavGroup，无需单独导出目录）
- **`src-electron/` 目录结构（严禁散文件）**：
  - `Service/`：Electron 主进程业务逻辑模块
    - `Window/index.ts`：窗口管理服务（创建、控制、状态管理）
    - `App/index.ts`：应用生命周期管理
    - `types.ts`：Service 层内部类型
  - `Preload/`：预加载脚本模块
    - `index.ts`：主预加载脚本，汇总暴露所有 API
    - `window.ts`：窗口控制 API 暴露
    - `types.ts`：Preload 层内部类型
  - `Ipc/`：IPC 通信处理模块
    - `WindowHandler.ts`：窗口控制 IPC 处理器
    - `AppHandler.ts`：应用配置 IPC 处理器
    - `types.ts`：IPC 处理器内部类型
  - `Types/`：**src-electron 内部类型**（对主进程内部使用，但对前端是外部类型）
    - `window.ts`：窗口相关类型（需同步到 `public/types/window/`）
    - `app.ts`：应用相关类型（需同步到 `public/types/app/`）
  - `electron-main.ts`：主进程入口（仅负责初始化和模块组装）
  - `electron-env.d.ts`：Electron 环境类型声明

**反模式**：
- ❌ 不要在 `GUI/components/` 下直接放 `Titlebar.vue`
- ❌ 不要在 `GUI/types/` 下直接放 `titlebar.ts`
- ❌ 不要在 `GUI/stores/` 下直接放 `navStore.ts`
- ❌ 不要创建过度抽象的 Store（如 AppStore，在功能未明确时）
- ❌ 不要为简单的模块创建独立的 types 目录（可直接放在模块的 types.ts 中）
- ❌ 不要在 `src-electron/` 下直接放 `windowService.ts` 等散文件
- ❌ 不要在 `src-electron/` 中将所有代码写在 `electron-main.ts` 中

### 决策点 2：如何实现 Electron 窗口控制？

**选择**：通过 Preload 脚本暴露有限的 IPC API，而非直接在渲染进程使用 remote

**理由**：Electron 12+ 已废弃 remote 模块，contextBridge + IPC 是官方推荐的安全方案

**实施要点**：
- 在 `src-electron/Preload/window.ts` 中暴露窗口控制 API：
  ```typescript
  import { contextBridge, ipcRenderer } from 'electron'
  import type { WindowControlAction } from '@types/window'
  
  export const exposeWindowAPI = () => {
    contextBridge.exposeInMainWorld('electronAPI', {
      windowControl: (action: WindowControlAction) => 
        ipcRenderer.invoke('window-control', action),
      onMaximizeChange: (callback: (isMaximized: boolean) => void) => 
        ipcRenderer.on('window-maximize-change', (_, isMaximized) => callback(isMaximized))
    })
  }
  ```
- 在 `src-electron/Preload/index.ts` 中汇总暴露：
  ```typescript
  import { exposeWindowAPI } from './window'
  
  exposeWindowAPI()
  // 其他 API 暴露...
  ```
- 在 `src-electron/Ipc/WindowHandler.ts` 中实现 IPC 处理器：
  ```typescript
  import { ipcMain, BrowserWindow } from 'electron'
  import type { WindowControlAction } from '../Types/window'
  
  export class WindowHandler {
    static register(win: BrowserWindow) {
      // 处理窗口控制请求
      ipcMain.handle('window-control', (event, action: WindowControlAction) => {
        const targetWin = BrowserWindow.fromWebContents(event.sender)
        if (!targetWin) return
        
        switch (action) {
          case 'minimize': targetWin.minimize(); break
          case 'maximize': 
            targetWin.isMaximized() ? targetWin.unmaximize() : targetWin.maximize()
            break
          case 'close': targetWin.close(); break
        }
      })
      
      // 监听窗口状态变化
      win.on('maximize', () => 
        win.webContents.send('window-maximize-change', true))
      win.on('unmaximize', () => 
        win.webContents.send('window-maximize-change', false))
    }
  }
  ```
- 在 `src-electron/electron-main.ts` 中注册处理器：
  ```typescript
  import { WindowHandler } from './Ipc/WindowHandler'
  
  app.whenReady().then(() => {
    const mainWindow = createWindow()
    WindowHandler.register(mainWindow)
    // 其他处理器注册...
  })
  ```
- 在 `public/types/electron.ts` 中定义全局类型：
  ```typescript
  declare global {
    interface Window {
      electronAPI?: ElectronWindowAPI
    }
  }
  ```

**反模式**：
- ❌ 不要在渲染进程中使用 `require('electron').remote`
- ❌ 不要暴露整个 `BrowserWindow` API（安全风险）
- ❌ 不要在组件中直接写 `ipcRenderer`（违反架构分层）

### 决策点 3：如何集成 Element Plus？

**选择**：全局自动导入（使用 `unplugin-vue-components` 和 `unplugin-auto-import`）

**理由**：避免在每个组件中手动导入，提升开发效率，减少样板代码

**实施要点**：
- 在 `package.json` 中添加依赖：
  ```json
  {
    "dependencies": {
      "element-plus": "^2.9.1"
    },
    "devDependencies": {
      "unplugin-vue-components": "^0.27.4",
      "unplugin-auto-import": "^0.18.5"
    }
  }
  ```
- 在 `quasar.config.ts` 的 `extendViteConf` 中添加插件：
  ```typescript
  import AutoImport from 'unplugin-auto-import/vite'
  import Components from 'unplugin-vue-components/vite'
  import { ElementPlusResolver } from 'unplugin-vue-components/resolvers'
  
  extendViteConf(viteConf) {
    viteConf.plugins = viteConf.plugins || []
    viteConf.plugins.push(
      AutoImport({ resolvers: [ElementPlusResolver()] }),
      Components({ resolvers: [ElementPlusResolver()] })
    )
  }
  ```
- 在 `Frontend/boot/element-plus.ts` 中添加全局配置：
  ```typescript
  import { boot } from 'quasar/wrappers'
  import 'element-plus/dist/index.css'
  import ElementPlus from 'element-plus'
  
  export default boot(({ app }) => {
    app.use(ElementPlus, { size: 'default', zIndex: 3000 })
  })
  ```
- 在 `quasar.config.ts` 的 `boot` 数组中注册：
  ```typescript
  boot: ['i18n', 'axios', 'element-plus']
  ```

**反模式**：
- ❌ 不要手动导入每个组件（如 `import { ElButton } from 'element-plus'`）
- ❌ 不要忘记导入 CSS 文件（会导致样式丢失）
- ❌ 不要在 `main.ts` 中配置（Quasar 使用 boot 文件机制）

### 决策点 4：如何处理类型导入符合 ESLint 规范？

**选择**：强制使用 `import type` 导入类型

**理由**：符合项目 ESLint 配置中的 `@typescript-eslint/consistent-type-imports` 规则

**实施要点**：
- 外部类型导入：
  ```typescript
  // ✅ 正确（从模块内部 types.ts 导入）
  import type { NavItem } from '../Shell/types'
  import type { ElectronWindowAPI } from '@types/window'
  
  // ❌ 错误（不要创建不必要的导出目录）
  import type { NavItem } from '@gui/types/navigation'
  ```
- 内部类型导入：
  ```typescript
  // ✅ 正确
  import type { TitlebarProps } from './types'
  
  // ❌ 错误
  import { TitlebarProps } from './types'
  ```
- 组件导入（非类型）：
  ```typescript
  // ✅ 正确（组件是值，不是类型）
  import GeneralTitlebar from '@gui/components/General.Titlebar/index.vue'
  
  // ❌ 错误
  import type GeneralTitlebar from '@gui/components/General.Titlebar/index.vue'
  ```

**反模式**：
- ❌ 不要混用值导入和类型导入（会触发 ESLint 错误）
- ❌ 不要使用 `import { type NavItem }` 语法（项目使用独立的 import type）

### 决策点 5：导航栏的 5/6 和 1/6 比例如何实现？

**选择**：使用 Flexbox 的 `flex-grow` 属性

**理由**：简单直观，无需计算具体高度，自适应窗口大小

**实施要点**：
- 导航栏容器使用 `display: flex; flex-direction: column`
- 上组使用 `flex-grow: 5`
- 下组使用 `flex-grow: 1`
- CSS 实现：
  ```scss
  .navbar-container {
    display: flex;
    flex-direction: column;
    height: 100%;
    
    .nav-group-top {
      flex-grow: 5;
      display: flex;
      flex-direction: column;
      gap: 8px;
      padding: 16px 0;
    }
    
    .nav-group-bottom {
      flex-grow: 1;
      display: flex;
      flex-direction: column;
      justify-content: flex-end;
      padding: 16px 0;
    }
  }
  ```

**反模式**：
- ❌ 不要使用固定高度（如 `height: calc(100% * 5 / 6)`）
- ❌ 不要使用绝对定位（不利于响应式）

### src-electron 目录结构详细说明

**【核心原则】**：src-electron 严格按业务模块组织，禁止散文件

**【目录职责】**：
1. **Service/**：主进程业务逻辑层
   - 负责：窗口创建与管理、应用配置、系统交互等核心业务
   - 示例模块：`Window/`、`App/`、`FileSystem/`、`SystemTray/`
   
2. **Preload/**：预加载脚本层
   - 负责：通过 contextBridge 安全地暴露 API 给渲染进程
   - 原则：每个业务域一个暴露模块（如 `window.ts`、`app.ts`）
   - 汇总：`index.ts` 负责调用所有暴露函数
   
3. **Ipc/**：IPC 通信处理层
   - 负责：处理来自渲染进程的 IPC 请求，调用 Service 层执行业务
   - 原则：一个业务域一个 Handler 类（如 `WindowHandler`、`AppHandler`）
   
4. **Types/**：类型定义层
   - 负责：定义 src-electron 内部使用的类型
   - 注意：跨进程共享的类型必须同步到 `public/types/` 下
   - 示例：主进程内部的配置类型、服务接口类型等

**【类型同步机制】**：
- `src-electron/Types/window.ts` 中定义 `WindowControlAction`（主进程内部）
- 同时在 `public/types/window/index.ts` 中导出相同定义（供前端使用）
- 确保类型一致性，避免主进程和渲染进程类型不匹配

**【模块依赖关系】**：
```
electron-main.ts（入口）
  ↓ 调用
Service/（业务逻辑）
  ↑ 被调用
Ipc/（IPC 处理器）
  ↑ 通过 ipcMain 注册
Preload/（API 暴露）
  → 通过 contextBridge 暴露给渲染进程
  → 渲染进程通过 window.electronAPI 调用
```
