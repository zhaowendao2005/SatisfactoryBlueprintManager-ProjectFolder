# SatisfactoryBlueprintManager 项目架构调整详细计划

> **说明**：本计划目前处于粗架构阶段，目标是设计一个通用的框架架构，便于后续项目直接复用。

## 📋 第一部分：设计概览

【目标】：将 `src` 目录重构为 `Frontend/GUI` 架构，明确职责分离，便于后续扩展。本架构设计为通用框架，可供其他项目复用。

【范围】：
- 在范围内：目录重命名、文件迁移、别名调整、路由简化、ESLint 命令配置、package.json 脚本调整
- 不在范围内：业务逻辑修改、新功能添加、测试用例编写

【技术栈决策】：
- 目录结构：`Frontend/GUI/{types,pages,stores,components,service}`（原因：与现有规则一致，分离 GUI 层与业务层）
- 路由：单文件路由配置（原因：仅负责对外路由映射，页面内部路由由页面组件处理）
- 类型组织：业务域内公共类型放在对应业务域目录（原因：类型与业务域耦合，便于维护）
- 日志脚本：使用 `run-with-logger.mjs` 包装所有开发命令（原因：统一日志管理）

【架构模式】：模块化分层架构（GUI层 / 业务服务层 / 路由层）

【核心约束】：
- 保持 Quasar 框架默认约定（如 `boot`、`i18n` 目录）
- 必须兼容 Electron 开发模式
- 所有路径别名必须同步更新
- 不得破坏现有功能

## 🏗️ 第二部分：模块划分与职责

### 目录结构树

**类型组织规则说明**：
- **外部类型**：跨模块/跨层级的业务类型，放在项目根目录级别的 `types/` 目录下（如跨 Frontend 和 src-electron 的类型）。外部类型通过别名导入（如 `@types`）。
- **内部类型**：仅在特定业务域内使用的类型，放在对应业务域目录的 `types/` 子目录中（如 `GUI/pages/Home/types/`）。内部类型使用相对路径导入。
- **通用规则**：components、stores、service 等模块也遵循相同的内部/外部类型规则，可在各自目录下创建 `types/` 子目录存放内部类型。

```
Frontend/（原 src/，职责：前端代码根目录）
  ├─ GUI/（职责：GUI 层代码，包含所有与界面相关的代码）
  │   ├─ types/（职责：GUI 层外部类型定义）
  │   │   └─ 外部类型：GUI 层公共类型，按业务域组织，如 Blueprint.ts, Project.ts
  │   │
  │   ├─ pages/（职责：页面组件，类似 DOM 树结构）
  │   │   ├─ Home/（职责：首页业务域）
  │   │   │   ├─ types/（职责：Home 页面内部类型，如 HomeState.ts）
  │   │   │   ├─ components/（职责：Home 页面专用组件）
  │   │   │   ├─ stores/（职责：Home 页面专用状态管理）
  │   │   │   └─ Index.vue（职责：处理路由、组合式函数、页面逻辑）
  │   │   ├─ Blueprint/（职责：蓝图业务域）
  │   │   │   ├─ types/（职责：Blueprint 页面内部类型）
  │   │   │   └─ Index.vue
  │   │   └─ ...（其他业务域页面）
  │   │
  │   ├─ components/（职责：可复用 GUI 组件）
  │   │   ├─ types/（职责：通用组件内部类型）
  │   │   └─ ...（通用组件）
  │   │
  │   ├─ stores/（职责：GUI 层状态管理）
  │   │   ├─ types/（职责：Store 内部类型）
  │   │   └─ ...（Pinia stores）
  │   │
  │   └─ service/（职责：GUI 层业务服务）
  │       ├─ types/（职责：Service 内部类型）
  │       └─ ...（调用后端 API 的服务层）
  │
  ├─ router/（职责：单文件路由配置，仅负责对外路由映射）
  │   └─ index.ts（职责：定义路由表，导入页面组件）
  │
  ├─ boot/（职责：Quasar 启动文件，保持不变）
  │   ├─ axios.ts
  │   └─ i18n.ts
  │
  ├─ i18n/（职责：国际化资源，保持不变）
  │   └─ ...
  │
  └─ App.vue（职责：应用根组件，迁移到 Frontend/App.vue）

注：静态资源应放在项目根目录的 `public/` 目录下（Electron 程序约定），而非 Frontend/assets/

### 关键模块职责说明

**GUI/types 模块**：
- 输入：业务需求定义的类型
- 输出：TypeScript 类型定义文件
- 关键逻辑：
  1. **GUI/types/**：存放 GUI 层的外部类型（跨页面/组件共享的类型），按业务域组织文件，如 `blueprint.ts`, `project.ts`
  2. **页面内部类型**：放在页面目录下的 `types/` 子目录中（如 `GUI/pages/Home/types/`），使用相对路径导入
  3. **组件内部类型**：放在组件目录下的 `types/` 子目录中（如 `GUI/components/Button/types/`），使用相对路径导入
  4. **跨层级外部类型**：如果类型需要跨 Frontend 和 src-electron，应放在项目根目录的 `types/` 目录下，通过别名 `@types` 导入
  5. 类型文件命名：业务域名.ts（外部类型）或与业务相关的描述性名称（内部类型）

**GUI/pages 模块**：
- 输入：路由参数、查询参数
- 输出：Vue 组件渲染结果
- 关键逻辑：
  1. 每个业务域一个目录，目录名使用 PascalCase
  2. 目录内必须包含 `Index.vue` 作为入口
  3. `Index.vue` 负责：处理路由逻辑、组合式函数、页面状态管理、子组件组合
  4. 页面内部如需嵌套路由，由页面组件内部处理（不依赖全局 router）

**router/index.ts 模块**：
- 输入：路由配置数组
- 输出：Vue Router 实例
- 关键逻辑：
  1. 合并原 `routes.ts` 内容到 `index.ts`
  2. 路由定义直接写在 `index.ts` 中，不使用单独 routes 文件
  3. 路由路径映射到 `GUI/pages/*/Index.vue`
  4. 保持 Quasar 的 `defineRouter` 包装

**别名配置模块**：
- 输入：路径别名映射规则
- 输出：Vite 别名配置（在 quasar.config.ts 中）
- 关键逻辑：
  1. `@gui` → `Frontend/GUI`
  2. `@gui/types` → `Frontend/GUI/types`
  3. `@gui/pages` → `Frontend/GUI/pages`
  4. `@gui/components` → `Frontend/GUI/components`
  5. `@gui/stores` → `Frontend/GUI/stores`
  6. `@gui/service` → `Frontend/GUI/service`
  7. `@router` → `Frontend/router`
  8. `@boot` → `Frontend/boot`
  9. `@i18n` → `Frontend/i18n`
  10. `@types` → 项目根目录 `types/`（跨层级外部类型）

注：静态资源通过 `public/` 目录访问，无需配置别名

## 🔌 第三部分：关键接口定义

/**
 * Quasar 配置文件中的 Vite 别名配置
 * @注意事项 必须在 extendViteConf 中配置，确保 TypeScript 和 Vite 都能识别
 */
interface ViteAliasConfig {
  '@gui': string              // Frontend/GUI 的绝对路径
  '@gui/types': string        // Frontend/GUI/types 的绝对路径
  '@gui/pages': string        // Frontend/GUI/pages 的绝对路径
  '@gui/components': string   // Frontend/GUI/components 的绝对路径
  '@gui/stores': string       // Frontend/GUI/stores 的绝对路径
  '@gui/service': string      // Frontend/GUI/service 的绝对路径
  '@router': string           // Frontend/router 的绝对路径
  '@boot': string             // Frontend/boot 的绝对路径
  '@i18n': string             // Frontend/i18n 的绝对路径
  '@types': string            // 项目根目录 types/ 的绝对路径（跨层级外部类型）
}

/**
 * package.json 脚本命令结构
 * @注意事项 所有 dev/build 命令都需要支持日志跟踪，使用 run-with-logger.mjs 包装
 */
interface PackageJsonScripts {
  'dev': string                    // 开发模式（带 ESLint）
  'dev:no-lint': string            // 开发模式（跳过 ESLint）
  'dev:electron': string           // Electron 开发模式（带 ESLint）
  'dev:electron:no-lint': string   // Electron 开发模式（跳过 ESLint）
  'build': string                  // 生产构建（带 ESLint）
  'build:electron': string         // Electron 构建（带 ESLint）
  'build:electron:no-lint': string // Electron 构建（跳过 ESLint）
  'create:summary': string         // 创建总结文件
  'lint': string                   // ESLint 检查
}

/**
 * 路由配置结构（router/index.ts）
 * @注意事项 单文件结构，所有路由定义直接写在 index.ts 中
 */
interface RouteConfig {
  routes: RouteRecordRaw[]  // 路由记录数组，直接定义在文件中
  createRouter: () => Router // 使用 defineRouter 包装的创建函数
}
```

## ⚠️ 第五部分：关键决策点与实施注意事项

### 决策点 1：如何处理现有文件迁移？

选择：先创建新目录结构，再迁移文件，最后删除旧目录

理由：避免文件丢失，便于回滚

实施要点：
- 步骤 1：创建 `Frontend/GUI/{types,pages,stores,components,service}` 目录
- 步骤 2：迁移 `src/stores/*` → `Frontend/GUI/stores/`
- 步骤 3：迁移 `src/components/*` → `Frontend/GUI/components/`
- 步骤 4：创建 `Frontend/GUI/pages/Home/Index.vue`，迁移 `src/pages/IndexPage.vue` 内容
- 步骤 5：创建 `Frontend/GUI/pages/Error/Index.vue`，迁移 `src/pages/ErrorNotFound.vue` 内容
- 步骤 6：迁移 `src/App.vue` → `Frontend/App.vue`
- 步骤 7：合并 `src/router/routes.ts` 到 `Frontend/router/index.ts`
- 步骤 8：迁移 `src/{boot,i18n,env.d.ts}` → `Frontend/`
- 步骤 9：删除 `src/` 目录（注意：`src/assets/` 目录也应删除，静态资源应使用 `public/` 目录）
- 步骤 10：更新所有配置文件中的路径引用

反模式：
- ❌ 不要直接重命名 `src` → `Frontend`（会破坏 Quasar 配置）
- ❌ 不要先删除再创建（风险高）

---

### 决策点 2：别名配置放在哪里？

选择：在 `quasar.config.ts` 的 `extendViteConf` 中配置 Vite 别名，在 `tsconfig.json` 中配置 TypeScript 路径映射

理由：Quasar 使用 Vite，需要同时配置 Vite 和 TypeScript

实施要点：
- Vite 别名：在 `quasar.config.ts` 的 `extendViteConf(viteConf)` 中添加 `viteConf.resolve.alias`
- TypeScript 路径：在 `tsconfig.json` 中添加 `compilerOptions.paths`
- 使用 `fileURLToPath` 和 `path.resolve` 生成绝对路径
- 确保别名路径指向 `Frontend/` 而非 `src/`

反模式：
- ❌ 不要只在 Vite 或 TypeScript 中配置（会导致类型检查或运行时错误）
- ❌ 不要使用相对路径别名（在不同文件深度下会失效）

---

### 决策点 3：如何构造跳过 ESLint 的命令？

选择：在 Quasar 命令后添加 `--skip-lint` 参数（如果支持），或使用环境变量禁用 ESLint 插件

理由：Quasar CLI 可能支持跳过 lint，或通过环境变量控制

实施要点：
- 检查 Quasar CLI 是否支持 `--skip-lint`：`quasar dev --skip-lint`
- 如果不支持，在 `quasar.config.ts` 的 `vitePlugins` 中条件性加载 `vite-plugin-checker`
- 使用环境变量 `SKIP_LINT=true` 控制是否加载 ESLint 插件
- package.json 脚本：`"dev:no-lint": "SKIP_LINT=true quasar dev"`

反模式：
- ❌ 不要直接注释掉 ESLint 配置（难以切换）
- ❌ 不要创建单独的配置文件（增加维护成本）

---

### 决策点 4：如何集成日志跟踪脚本？

选择：使用 `run-with-logger.mjs` 包装所有开发/构建命令

理由：统一日志管理，便于调试

实施要点：
- 脚本格式：`node Script/run-with-logger.mjs --name <script-name> -- <command> [args...]`
- dev 命令：`node Script/run-with-logger.mjs --name dev -- quasar dev`
- dev:electron 命令：`node Script/run-with-logger.mjs --name dev-electron -- quasar dev -m electron`
- build:electron 命令：`node Script/run-with-logger.mjs --name build-electron -- quasar build -m electron`
- 日志输出到 `.log/<script-name>/<timestamp>.log`

反模式：
- ❌ 不要直接调用 `quasar` 命令（丢失日志）
- ❌ 不要在不同命令中使用不同的日志脚本（不一致）

---

### 决策点 5：路由文件如何简化？

选择：合并 `routes.ts` 到 `index.ts`，路由定义直接写在文件中

理由：单文件更简单，符合“仅负责对外路由”的要求

实施要点：
- 将 `src/router/routes.ts` 的内容复制到 `Frontend/router/index.ts`
- 删除 `routes.ts` 文件
- 在 `index.ts` 中直接定义 `routes` 常量数组
- 路由路径使用别名：`@gui/pages/Home/Index.vue`

反模式：
- ❌ 不要保留 `routes.ts`（违背单文件要求）
- ❌ 不要在每个页面目录中创建路由文件（路由统一管理）
