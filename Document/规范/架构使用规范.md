# Frontend/GUI 架构使用规范

> 本文档说明如何使用 `Frontend/GUI` 架构规范进行开发

## 📁 目录结构规范

### 基本目录结构

```
Frontend/
  ├─ GUI/
  │   ├─ types/          # GUI 层外部类型（跨页面/组件共享）
  │   ├─ pages/          # 页面组件
  │   ├─ components/     # 可复用组件
  │   ├─ stores/         # Pinia stores
  │   └─ service/        # 业务服务层
  ├─ router/             # 路由配置（单文件）
  ├─ boot/               # Quasar 启动文件
  ├─ i18n/               # 国际化资源
  └─ App.vue             # 应用根组件
```

### 页面目录结构

每个业务域页面应有以下结构：

```
GUI/pages/{Domain}/
  ├─ Index.vue           # 页面入口组件（必需）
  ├─ types/              # 页面内部类型（可选）
  ├─ components/         # 页面专用组件（可选）
  ├─ stores/             # 页面专用状态管理（可选）
  └─ service/            # 页面专用服务（可选）
```

## 🔤 类型组织规范

### 内部类型 vs 外部类型

**核心原则**：内部类型与外部类型是相对概念，取决于业务域的层级关系。

#### 判断规则

1. **内部类型**：仅在当前业务域内使用
   - 位置：业务域目录下的 `types/` 子目录
   - 导入方式：相对路径（如 `./types/HomeState`）

2. **外部类型**：跨文件/跨模块共享
   - **GUI 层外部类型**：`GUI/types/` 目录，通过别名 `@gui/types` 导入
     - 仅用于跨页面/组件共享的类型（如窗口控制、全局配置等）
   - **业务域外部类型**：业务域目录下的 `types.ts` 文件，通过相对路径导入
     - 示例：`GUI/pages/MainWindow/Shell/types.ts` 存放 MainWindow Shell 层共享类型
     - 原则：**无需创建独立的 types 目录**，直接放在模块的 `types.ts` 中
   - **跨层级外部类型**：`public/types/` 目录，通过别名 `@types` 导入
     - 仅用于跨 Frontend 和 src-electron 的类型（如 Electron IPC API）

#### 示例

```typescript
// 场景：GUI/service/BusinessA/ 业务模块

// 1. BusinessA 内部类型（仅在 BusinessA 某个文件内使用）
// 位置：GUI/service/BusinessA/utils/types.ts
// 导入：import type { InternalUtil } from './utils/types'

// 2. BusinessA 外部类型（BusinessA 内多个文件共享）
// 位置：GUI/service/BusinessA/types.ts（或 Shell/types.ts）
// 导入：import type { BusinessAApi } from '../types' 或 './Shell/types'
// ⚠️ 注意：不要创建独立的 types 目录，直接放在模块的 types.ts 中

// 3. GUI 层外部类型（跨页面/组件共享）
// 位置：GUI/types/blueprint.ts
// 导入：import type { Blueprint } from '@gui/types/blueprint'

// 4. 跨层级类型（跨 Frontend 和 src-electron）
// 位置：public/types/shared.ts
// 导入：import type { ElectronEvent } from '@types/shared'
```

## 📝 代码编写规范

### 页面组件编写

```vue
<!-- GUI/pages/Home/Index.vue -->
<template>
  <q-page>
    <!-- 页面内容 -->
  </q-page>
</template>

<script setup lang="ts">
// 1. 导入外部类型（使用别名）
import type { User } from '@gui/types/user'
import type { ApiResponse } from '@types/api'

// 2. 导入内部类型（使用相对路径）
import type { HomeState } from './types/HomeState'

// 3. 导入组件（使用别名）
import { UserCard } from '@gui/components/UserCard'

// 4. 导入服务（使用别名）
import { userService } from '@gui/service/user'

// 5. 导入 stores（使用别名，命名必须明确指向具体模块）
import { useMainWindowNavbarStore } from '@gui/stores/MainWindow.Navbar'

// 页面逻辑...
</script>
```

### 组件编写

```vue
<!-- GUI/components/Button/Button.vue -->
<template>
  <q-btn :label="label" />
</template>

<script setup lang="ts">
// 组件内部类型使用相对路径
import type { ButtonProps } from './types/ButtonProps'

// GUI 层外部类型使用别名
import type { Theme } from '@gui/types/theme'

defineProps<ButtonProps>()
</script>
```

### 服务编写

```typescript
// GUI/service/user/index.ts
import type { User } from '@gui/types/user'
import type { ApiResponse } from '@types/api'

export const userService = {
  async getUser(id: string): Promise<ApiResponse<User>> {
    // 服务实现
  }
}
```

### Store 编写

**【命名规范】**：Store 目录命名必须明确指向具体业务模块，避免过度抽象的命名。

```typescript
// ✅ 正确：明确指向具体业务模块
// GUI/stores/MainWindow.Navbar/index.ts
import { defineStore } from 'pinia'
import type { NavItem } from '../../pages/MainWindow/Shell/types'

export const useMainWindowNavbarStore = defineStore('mainWindowNavbar', {
  state: (): { activeRoute: string; navItems: NavItem[] } => ({
    activeRoute: '/welcome',
    navItems: []
  }),
  actions: {
    setActiveRoute(route: string) {
      this.activeRoute = route
    }
  }
})

// ❌ 错误：命名过于抽象，无法明确指向具体模块
// GUI/stores/navigation/index.ts
// export const useNavStore = ... // 这是哪个导航栏？

// ❌ 错误：过度设计，功能未明确时创建全局 Store
// GUI/stores/app/index.ts
// export const useAppStore = ... // 如果只是硬编码的应用名称，无需 Store
```

**【Store 组织原则】**：
- **明确指向**：Store 目录名应明确指向具体业务模块（如 `MainWindow.Navbar`、`Blueprint.Editor`）
- **避免抽象**：不要使用过度抽象的命名（如 `navigation`、`app`、`common`）
- **避免过度设计**：功能未明确时，不要创建全局 Store（如硬编码的应用名称可直接写在组件中）
- **模块化**：每个 Store 目录下包含 `index.ts`（Store 实现）和 `types.ts`（Store 专用类型）

## 🛣️ 路由配置规范

### 路由定义

路由配置统一在 `Frontend/router/index.ts` 中定义：

```typescript
import type { RouteRecordRaw } from 'vue-router'

const routes: RouteRecordRaw[] = [
  {
    path: '/',
    component: () => import('@gui/pages/Home/Index.vue')
  },
  {
    path: '/blueprint',
    component: () => import('@gui/pages/Blueprint/Index.vue')
  },
  {
    path: '/:catchAll(.*)*',
    component: () => import('@gui/pages/Error/Index.vue')
  }
]

export default routes
```

**注意**：
- 路由路径使用别名 `@gui/pages/{Domain}/Index.vue`
- 页面内部路由由页面组件自行处理，不依赖全局 router

## 📦 别名使用规范

### 可用别名

| 别名 | 路径 | 用途 |
|------|------|------|
| `@gui` | `Frontend/GUI` | GUI 层根目录 |
| `@gui/types` | `Frontend/GUI/types` | GUI 层外部类型 |
| `@gui/pages` | `Frontend/GUI/pages` | 页面组件 |
| `@gui/components` | `Frontend/GUI/components` | 通用组件 |
| `@gui/stores` | `Frontend/GUI/stores` | Pinia stores |
| `@gui/service` | `Frontend/GUI/service` | 业务服务 |
| `@router` | `Frontend/router` | 路由配置 |
| `@boot` | `Frontend/boot` | 启动文件 |
| `@i18n` | `Frontend/i18n` | 国际化资源 |
| `@types` | `public/types` | 跨层级外部类型 |

### 别名使用示例

```typescript
// ✅ 正确：使用别名导入外部类型
import type { User } from '@gui/types/user'
import type { ApiResponse } from '@types/api'

// ✅ 正确：使用别名导入组件
import { UserCard } from '@gui/components/UserCard'

// ✅ 正确：使用相对路径导入内部类型
import type { HomeState } from './types/HomeState'
import type { NavItem } from '../Shell/types'  // 模块内共享类型

// ✅ 正确：模块内类型直接放在 types.ts 中，使用相对路径导入
import type { NavItem } from './Shell/types'  // MainWindow/Shell/types.ts

// ❌ 错误：不要使用相对路径跨层级导入
import type { User } from '../../types/user'

// ❌ 错误：不要直接使用路径别名导入内部类型
import type { HomeState } from '@gui/pages/Home/types/HomeState'

// ❌ 错误：不要创建不必要的 types 目录进行层层导出
import type { NavItem } from '@gui/types/navigation'  // 应该放在 Shell/types.ts 中
```

## 🎯 最佳实践

### 1. 类型组织

- **小范围共享**：使用相对路径导入内部类型（如 `./types/HomeState`）
- **模块内共享**：放在模块的 `types.ts` 中，使用相对路径导入（如 `./Shell/types`）
  - **原则**：无需创建独立的 `types/` 目录，直接放在模块的 `types.ts` 文件中
- **大范围共享**：使用 `@gui/types` 导入 GUI 层外部类型（仅跨页面/组件）
- **跨层级共享**：使用 `@types` 导入跨层级类型（跨 Frontend 和 src-electron）

### 2. 组件组织

- **通用组件**：放在 `GUI/components/`，使用别名导入
- **页面专用组件**：放在页面目录下的 `components/`，使用相对路径导入

### 3. 服务组织

- **通用服务**：放在 `GUI/service/`，使用别名导入
- **页面专用服务**：放在页面目录下的 `service/`，使用相对路径导入

### 4. 状态管理

- **全局状态**：放在 `GUI/stores/{具体模块}/`，命名必须明确指向业务模块
  - 示例：`stores/MainWindow.Navbar/`、`stores/Blueprint.Editor/`
  - 导入：`import { useMainWindowNavbarStore } from '@gui/stores/MainWindow.Navbar'`
- **页面状态**：放在页面目录下的 `stores/`，或使用组合式函数
- **避免过度设计**：功能未明确时，不要创建全局 Store（如应用名称、版本号等硬编码值）

## ⚠️ 注意事项

1. **静态资源**：放在 `public/` 目录下，直接通过 `/` 路径访问，无需配置别名

2. **类型判断**：不确定时，优先使用相对路径（内部类型），需要跨文件共享时再提升为外部类型

3. **类型组织简化**：
   - **模块内类型**：直接放在模块的 `types.ts` 文件中（如 `Shell/types.ts`）
   - **避免层层导出**：不要为简单模块创建独立的 `types/` 目录进行层层导出
   - **示例**：`GUI/pages/MainWindow/Shell/types.ts` 存放 Shell 层所有共享类型，无需创建 `types/navigation/` 目录

4. **Store 命名明确性**：
   - **必须明确指向**：Store 目录名应明确指向具体业务模块（如 `MainWindow.Navbar`）
   - **避免抽象命名**：不要使用 `navigation`、`app`、`common` 等过度抽象的命名
   - **避免过度设计**：功能未明确时，不要创建全局 Store（如硬编码的应用名称）

5. **别名一致性**：确保 Vite 和 TypeScript 配置中的别名一致

6. **路径深度**：避免过深的相对路径，超过 3 层应考虑使用别名

## 🚫 反模式示例

### 1. Store 命名过于抽象

```typescript
// ❌ 错误：命名过于抽象，无法明确指向具体模块
GUI/stores/navigation/index.ts
GUI/stores/app/index.ts

// ✅ 正确：明确指向具体业务模块
GUI/stores/MainWindow.Navbar/index.ts
GUI/stores/Blueprint.Editor/index.ts
```

### 2. 过度设计 Store

```typescript
// ❌ 错误：功能未明确时创建全局 Store
// GUI/stores/app/index.ts
export const useAppStore = defineStore('app', {
  state: () => ({
    appName: 'Satisfactory Blueprint Manager',  // 硬编码值，无需 Store
    version: '1.0.0'
  })
})

// ✅ 正确：直接硬编码或使用常量
// GUI/pages/MainWindow/Shell/MainWindow.TitleBar/index.vue
<General.Titlebar title="Satisfactory Blueprint Manager" />
```

### 3. 不必要的类型目录

```typescript
// ❌ 错误：为简单模块创建独立的 types 目录
GUI/types/navigation/index.ts  // 导出 NavItem、NavGroup

// ✅ 正确：类型直接放在模块的 types.ts 中
GUI/pages/MainWindow/Shell/types.ts  // 包含 NavItem、NavGroup 等 Shell 层类型
```

### 4. Store 散文件

```typescript
// ❌ 错误：在 stores 目录下直接放置文件
GUI/stores/navStore.ts
GUI/stores/appStore.ts

// ✅ 正确：按业务模块组织目录
GUI/stores/MainWindow.Navbar/index.ts
GUI/stores/MainWindow.Navbar/types.ts
```
