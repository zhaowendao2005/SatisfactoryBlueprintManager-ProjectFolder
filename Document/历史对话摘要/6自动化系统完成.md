## 踩的坑与经验总结

### 坑1：blueprintId 传递错误
**问题**：详情面板使用 `node.blueprintId || node.id`，但解析时使用的是 `node.id`
**原因**：`node.blueprintId` 是原始蓝图ID，而解析文件使用的是激活后的 `node.id`
**解决**：直接使用 `node.id` 作为 `blueprintId`
**经验**：确保数据流中 ID 的一致性

### 坑2：使用蓝图功能使用错误的配置
**问题**：`useBlueprint` 使用 `configs[0].id` 而不是用户选中的配置
**原因**：没有从 Store 获取当前选中的配置
**解决**：使用 `AutomationConfigStore.currentConfigId`
**经验**：跨模块访问状态时，应该使用 Store 而不是直接调用 API

### 坑3：ParseProgressDialog 类型错误
**问题**：`setResult` 方法创建了 mock 的 `ParseProgressInfo` 对象
**原因**：类型混淆，`setResult` 应该接收 `ParseResult` 而不是 `ParseProgressInfo`
**解决**：直接赋值 `parseResult` 到 `result.value`
**经验**：仔细区分相似类型的用途

### 坑4：导入路径错误
**问题**：`BlueprintInfoController` 中导入路径层级错误
**原因**：相对路径计算错误
**解决**：修正相对路径层级
**经验**：使用路径别名可以避免路径错误

## 架构决策记录

### 决策1：懒加载而非缓存
**选择**：点击详细信息时从磁盘读取，不缓存
**理由**：数据量大，缓存占用内存；懒加载按需加载更高效
**实施要点**：
- 移除所有缓存逻辑
- 在 `watch` 中监听 `blueprintId` 变化
- 每次变化时从磁盘读取

### 决策2：主进程解析
**选择**：在主进程执行解析任务
**理由**：解析是 CPU 密集型任务，在主进程执行不阻塞渲染进程
**实施要点**：
- 使用 IPC 通信
- 使用 EventEmitter 广播进度
- 渲染进程监听进度更新

### 决策3：完整对象存储
**选择**：存储完整的 `blueprint` 对象而非仅元数据
**理由**：未来可能需要更多信息，完整存储更灵活
**实施要点**：
- `BlueprintInfo` 接口包含完整的 `blueprint` 对象
- 格式化工具负责提取和格式化
